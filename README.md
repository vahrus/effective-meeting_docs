# Эффективное совещание

**Интерактивный симулятор управленческих решений**

**Эффективное совещание: перестаньте воровать время компании**

От вопроса «нужна ли встреча?» до решения, протокола и контроля договорённостей.

> Пользователь не отвечает на тестовые вопросы о правильном совещании — он проводит его и работает с последствиями собственных решений.

Главный сценарий: [`/simulator/egor`](http://localhost:3000/simulator/egor)

## Что это

«Эффективное совещание» — practice-first симулятор полного жизненного цикла рабочей встречи.

Пользователь управляет действиями Егора, руководителя проекта «Горизонт». Команде предстоит выбрать поставщика и превратить обсуждение в работающий план: определить формат встречи, собрать нужную экспертизу, подготовить участников, провести разговор, зафиксировать решение и довести обязательства до результата.

Это не набор независимых ситуационных вопросов. Каждый выбор меняет состояние мира, с которым пользователь столкнётся дальше.

Learner-facing помощник — **Агроник**. Внутренний стабильный speaker ID `tsosik` используется только как технический идентификатор сценария.

## Почему обычного курса недостаточно

Линейный курс хорошо объясняет термины, но редко показывает, что происходит между управленческим решением и его отложенным эффектом.

В симуляторе:

- теория проверяется действием, а не финальным тестом;
- последствия могут проявиться спустя несколько сцен;
- слабое решение не останавливает прохождение;
- ошибку можно заметить и исправить;
- система помнит и исходную ошибку, и последующее восстановление;
- итоговый профиль строится по истории поведения.

Например, отсутствие нужной экспертизы обнаруживается позже как пробел в данных, а нехватка времени на решение превращается в реальное давление к концу встречи. Пользователь не выбирает подпись «неправильно» — он создаёт условия следующей сцены.

## Как работает симулятор

```text
До совещания
    → Во время совещания
        → После совещания
            → Финал
```

Симулятор проводит полный цикл: подготовка → проведение → решение → фиксация → контроль → рефлексия.

Выборы могут влиять на:

- состав и подготовленность участников;
- доступную информацию и готовность к встрече;
- будущие события и отложенные последствия;
- время, фокус, доверие и напряжение;
- качество решения и конкретность поручений;
- протокол, контроль и фактическое исполнение.

Служебные метрики не превращены в постоянную панель баллов. Во время прохождения пользователь видит ситуацию и её проявления, а структурированный разбор получает после завершения цикла.

## Путь пользователя

| Этап | Что происходит | Что тренируется |
|---|---|---|
| **01. Фильтр встречи** (`meeting-filter`) | Нужно ли собирать группу вообще | Выбор подходящего формата совместной работы |
| **02. Архитектура встречи** (`idoarrt`) | Цель, результат, повестка, состав, роли, правила и время | Проектирование встречи до входа в переговорную |
| **03. Участники и подготовка** (`prework`) | Что приглашённые участники должны подготовить заранее | Работа с экспертизой и качеством входных данных |
| **04. Проверка готовности** (`readiness`) | Можно ли начинать встречу или нужно снять препятствие | Раннее обнаружение и устранение рисков |
| **05. Синхронизация** (`synchronization`) | Общая рамка в начале разговора | Ясное намерение, результат, роли и правила |
| **06. Фокус** (`focus`) | Смежные темы и ограниченное время | Удержание предмета встречи и парковка вопросов |
| **07. Взаимодействие** (`interaction`) | Доминирование, молчание и разные позиции | Вовлечение и конструктивная работа с разногласиями |
| **08. Решение и действие** (`decision`) | Выбор, основания, последствия и поручения | Переход от обсуждения к обязательству |
| **09. Протокол** (`protocol`) | Результаты вместо стенограммы | Сохранение решения, владельцев и сроков |
| **10. Контроль договорённостей** (`follow-up`) | Статусы, препятствия и адаптация | Доведение договорённости до результата |
| **11. Итоги кейса** (`evaluation`) | Объяснимая evidence-based оценка и управленческий профиль | Рефлексия по фактическим действиям |
| **12. Что это было на самом деле** (`reveal`) | Сюжетный поворот связывает симуляцию с рабочей реальностью | Переосмысление цены управленческих решений |
| **13. Финал** (последний этап `reveal`) | Итоговый message, Агроник и повторное прохождение | Перенос опыта в следующую рабочую встречу |

README намеренно не раскрывает правильный маршрут и детали финального поворота.

## Что делает симуляцию «живой»

### Последствия решений

Выбор не только переключает следующий экран. Он меняет участников, факты, риски, время, поведение группы, качество обязательств и дальнейший маршрут.

### Отложенные последствия

Решение на этапе подготовки может проявиться только во время обсуждения или после встречи:

```text
не пригласили нужную экспертизу
    → позже не хватает данных для обоснованного выбора

не оставили резерв времени
    → решение принимается под реальным давлением
```

Это связывает ранние и поздние этапы сильнее, чем обычный branching quiz.

### Repair-модель

Симулятор различает три истории:

1. сильное действие с самого начала;
2. ошибку без исправления;
3. ошибку, её последствие и последующее восстановление ситуации.

Repair добавляет новое свидетельство обучения, но не стирает первоначальную историю. Поэтому итоговый разбор может показать не только результат, но и способность руководителя корректировать траекторию.

### No Game Over

Слабый выбор не завершает игру. Пользователь продолжает работать с миром, который сам создал: неполной информацией, неясной ответственностью, потерянным временем или сложным исполнением.

Это безопасная среда для эксперимента без обесценивающего «вы проиграли».

### Evidence-based feedback

Внутри сценария разделены два типа истории:

- **Evidence** отвечает на вопрос: «Что реально сделал пользователь?»
- **Flags и domain state** отвечают на вопрос: «Что теперь истинно в мире?»

Evaluation читает накопленную историю и не переписывает её. Finale использует уже полученный результат и не создаёт новую оценку.

Оценка учитывает контекст конкретного прохождения: фактический состав участников, назначенный и выполненный pre-work, отсутствие обязательной экспертизы и релевантность событий конкретному участнику. Поэтому исключённый человек не считается присутствовавшим, а неназначенная работа не оценивается как невыполненное обещание.

## Что получает участник

### Управленческий профиль

После прохождения формируется один из шести профилей:

- Архитектор решения;
- Фасилитатор;
- Сильный организатор;
- Решительный лидер;
- Импровизатор;
- Системный координатор.

Это не результат отдельного опросника. Профиль выбирается по evidence всей симуляции: от подготовки до follow-up.

Для очень слабого результата learner-facing синтез остаётся профессиональным и развивающим: внутренний профиль сохраняется, но текст не приписывает пользователю устойчивые навыки, которых не подтверждает история действий.

### Восемь компетенций

1. Подготовка
2. Структура встречи
3. Фокус
4. Вовлечение
5. Работа с разногласиями
6. Качество решений
7. Ответственность
8. Доведение до результата

Итог включает сильные стороны, зоны развития, repair-истории и объяснение того, как поведение повлияло на результат.

Learner-facing copy локализован на русский язык, включая числительные и склонения. Варианты выбора сформулированы как реалистичные управленческие альтернативы; сильный вариант не должен выделяться очевидной длиной или тестовой формулировкой.

### Экономика времени

Симулятор показывает стоимость встречи в командном времени, а не в рублях:

```text
6 человек × 43 минуты
= 258 человеко-минут
= 4 ч 18 мин командного времени
```

Ожидание до перенесённой встречи в расчёт не входит: учитывается фактическая длительность самой встречи. Центральная идея — время команды является управленческим ресурсом.

## Reality Reveal и Finale

После Evaluation сценарий переходит в Reality Reveal, а затем автоматически фиксирует completion при входе в финальное состояние.

Последний экран содержит:

- заголовок **«Симулятор пройден.»**;
- визуальный hero с Егором;
- основной итоговый message;
- карточку Агроника;
- единственный CTA **«Пройти симуляцию ещё раз»**, который выполняет полный reset/replay.

Finale читает уже рассчитанный результат и не изменяет gameplay history или score.

## Presentation и assets

Learner-facing маршрут `/simulator/egor` всегда использует `corporate-light`; переключатель темы и effects-controls на нём отсутствуют. Общий theme registry (`src/themes/theme-registry.ts`) по-прежнему содержит `corporate-light` и `rshb-dark`: тёмная тема не удалена и остаётся доступной программно и в legacy `/simulator`.

Runtime-портреты Егора и пяти участников — оптимизированные WebP 512×512; canonical paths собраны в `src/themes/egor-portrait-assets.ts`. Семь состояний Агроника используют WebP 640×640 и зарегистрированы в `src/themes/corporate-light.ts`. Локальные master assets хранятся вне runtime-каталога `public`, в исключённом из публикации `assets-original/`.

## Почему это интересно L&D и бизнесу

- **Practice-first обучение.** Участник тренирует управленческое поведение, а не воспроизведение терминов.
- **Причинная учебная модель.** Обратная связь объясняет последствия, а не только правильность выбранной кнопки.
- **Безопасный эксперимент.** Нет Game Over; слабые решения становятся материалом для дальнейшей работы.
- **Индивидуальный разбор.** Профиль и рекомендации собираются из фактической истории прохождения.
- **Полный цикл.** Симуляция не заканчивается решением в переговорной — она доходит до протокола и исполнения.
- **Детерминированное прохождение.** Одинаковая история действий даёт одинаковый результат.
- **Без runtime-зависимости от LLM или внешнего API.** Игровая логика выполняется в браузере и не требует отдельного backend.
- **Конкурсная corporate-light подача.** Основной маршрут имеет единый learner-facing интерфейс без служебного переключателя темы.
- **Встраивание в обучение.** Сценарий можно размещать в iframe внутри LMS или iSpring Web Object как самостоятельную практику или часть blended/e-learning курса.

Важно: проект поддерживает размещение симулятора внутри LMS, но не реализует передачу SCORM/xAPI completion или результатов в LMS.

## Технологические особенности

- причинно-связанный сценарий вместо набора изолированных веток;
- participant-aware события: исключённый участник не изображается присутствующим на встрече;
- delayed events с prerequisites и однократным потреблением;
- idempotent effects для повторных кликов и восстановления после reload;
- Zustand persist с Zod-валидацией сохранения;
- чистые функции Evaluation и Finale;
- единая presentation-система тем и Living Workspace;
- поддержка `prefers-reduced-motion`;
- полностью клиентская игровая логика.

## Архитектура

```text
                        /simulator/egor
                               │
                      Egor UI / Workspaces
                               │
                     Egor Scenario Runtime
                               │
             ┌─────────────────┴─────────────────┐
             │                                   │
      Scenario Logic                       Generic Engine
      Egor-specific                        reusable primitives
      content / routing                    events / choices
      participants / evidence              effects / conditions
      evaluation / finale                  scheduler / idempotency
             │                                   │
             └─────────────────┬─────────────────┘
                               │
                    Zustand Persist + Zod
                               │
              Evaluation (pure read of history)
                               │
                 Finale (pure read of result)
```

### Generic Engine

`src/simulator/engine/` содержит универсальные primitives:

- events и choices;
- effects и transitions;
- conditions и flags;
- evidence;
- delayed events и scheduler;
- idempotency через историю обработанных событий, выборов и effects.

Движок не знает о Егоре, IDOARRT, поставщиках, конфликте, протоколе или Management Profile.

### Egor Scenario

`src/simulator/scenarios/egor/` владеет предметной логикой:

- контентом и маршрутизацией;
- участниками и подготовкой;
- поведением встречи;
- решениями и поручениями;
- протоколом и follow-up;
- evidence и Evaluation;
- Reality Reveal и Finale.

UI нового сценария находится преимущественно в `src/components/egor/`, а route/client — в `src/app/simulator/egor/`.

### Persist и idempotency

Основной сценарий сохраняется в `localStorage`:

```text
effective-meeting-egor-v11
```

Контракт состояния имеет версию `11`; это persist/runtime version, а не придуманная semantic-версия учебного сюжета.

Повторный click, reload или hydrate не должны повторно списывать время, добавлять evidence, создавать поручения или запускать уже потреблённые последствия. Это обеспечивают уникальные effect keys, обработанные event/choice IDs и hydrate-safe defaults.

### Evaluation

Оценка компетенции рассчитывается по весам positive и negative evidence:

```text
clamp(0, 100, round(60 + 4 × positiveWeight − 5 × negativeWeight))
```

Итог агрегирует восемь компетенций с весами `15 / 10 / 15 / 10 / 15 / 15 / 10 / 10%`. Evaluation читает gameplay history и не изменяет её.

### Legacy isolation

В репозитории сохранён предыдущий симулятор:

| Реализация | Route | Основной код | Persist |
|---|---|---|---|
| **Egor — основной продукт** | `/simulator/egor` | `src/simulator/engine/`, `src/simulator/scenarios/egor/`, `src/components/egor/` | `effective-meeting-egor-v11` |
| **Legacy** | `/simulator` | `src/features/`, `src/data/scenario.json`, legacy-компоненты | `effective-meeting-game-state-v10` |

Persist-ключи изолированы и не мигрируют друг в друга. `scenario.json`, Meeting Engine и Action Control Engine из `src/features/` относятся к legacy и не являются источником Egor-сценария.

## Встраивание в LMS / iSpring

Основной рекомендуемый route:

```text
https://<domain>/simulator/egor?embed=1
```

Поддерживается и iSpring-вариант:

```text
https://<domain>/simulator/egor?source=ispring
```

Оба параметра включают embed-режим: убирают внешний branding shell, используют компактную рамку и активируют передачу высоты родительскому окну.

Embed использует единый `corporate-light` canvas для `html`, `body` и shell. Высота не фиксируется: `ResizeObserver` сообщает родителю максимум из фактической высоты контента и responsive minimum — `720px` для desktop (`≥1024px`) и `640px` для compact viewport. Длинные сцены могут превышать minimum; основная прокрутка остаётся на странице курса.

### Пример iframe

```html
<iframe
  id="effective-meeting"
  src="https://<domain>/simulator/egor?embed=1"
  title="Симулятор «Эффективное совещание»"
  width="100%"
  style="border: 0; display: block; width: 100%;"
  loading="lazy"
  allowfullscreen
></iframe>

<script>
  const frame = document.querySelector("#effective-meeting");

  window.addEventListener("message", (event) => {
    if (event.source !== frame.contentWindow) return;
    if (event.data?.type === "effective-meeting:height") {
      frame.style.height = `${event.data.height}px`;
    }
  });
</script>
```

Симулятор отправляет родителю сообщение:

```js
{
  type: "effective-meeting:height",
  height: 842
}
```

Тип сообщения и responsive minimum определены в `src/features/embed/use-iframe-height.ts`. Повторные сообщения с неизменившейся высотой не отправляются.

При входе в финальное состояние embed дополнительно отправляет generic host signal:

```js
{
  type: "effective-meeting:complete",
  version: 1,
  simulator: "egor"
}
```

Это стабильный application-level contract, а не SCORM/xAPI-вызов; подтверждение LMS для локального completion не требуется.

### Ограничения интеграции

- Прогресс хранится в `localStorage` браузера, а не в учётной записи LMS.
- Cross-domain iframe может ограничивать storage политиками браузера или LMS.
- SCORM/xAPI reporting и синхронизация результатов с LMS не реализованы.
- Прохождение следует проверить в preview и production-контуре конкретной LMS.

### Frame policy

`next.config.ts` сейчас отправляет:

```http
Content-Security-Policy: frame-ancestors *
```

Это разрешает встраивание с любых origins. Для корпоративного production-контура рекомендуется заменить `*` утверждённым списком доменов LMS.

## Темы

| ID | Назначение |
|---|---|
| `corporate-light` | Единственная learner-facing тема конкурсного маршрута `/simulator/egor` |
| `rshb-dark` | Тёмная брендированная тема, сохранённая для shared/legacy использования |

Theme selector на Egor route отсутствует; route-level lock не изменяет shared preference. Общая архитектура продолжает поддерживать обе темы, а `rshb-dark` остаётся default в shared registry и доступна legacy `/simulator`. Технически shared `themeId` хранится под legacy-ключом `effective-meeting-game-state-v10`; в Egor persist v11 тема не дублируется.

### Self-hosted

```bash
npm ci
npm run build
npm start
```

Приложение по умолчанию слушает порт `3000`; для корпоративного контура обычно используется HTTPS reverse proxy. Игровой backend или база данных для прохождения не требуются.
